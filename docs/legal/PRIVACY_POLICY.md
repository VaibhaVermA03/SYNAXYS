## 2. The most important thing: your code is sent to third parties

> **To analyse pull requests and to search your code, SYNAXYS sends parts of your source code to OpenAI, and stores code excerpts, vectors (“embeddings”) and metadata of indexed repositories at Pinecone. This is not optional for the features that use them. Pattern-based secret redaction reduces, but cannot eliminate, the chance that sensitive text is sent. Do not connect repositories whose code you are not allowed to share with these processors.**

- OpenAI receives code from pull request diffs (for reviews) and code chunks and search queries (for indexing and search). See section 5.
- Pinecone stores indexed code chunks (up to 1,500 characters of text each), their file path, repository name, branch, commit and line range, together with the vector. See section 6.
- Your own database (hosted with the providers listed in section 9) stores review results, which quote your code. See section 7.
- Embeddings are numeric representations of text. We do not claim that they cannot reveal information about the text they were made from: treat them as potentially sensitive.

## 4. Repository data we access and the GitHub permissions we need

SYNAXYS works through a GitHub App that you or your organisation install on selected repositories (or all of them). The App asks for:

- Metadata: read (repository names and basic information).
- Contents: read (to read files for indexing and to read the files around a change).
- Pull requests: read and write (to read pull requests and diffs, to read existing review comments so duplicates are not posted, and to post and delete review comments written by SYNAXYS).

It receives webhook events for pull requests, pushes, and installation changes. Comments appear on GitHub as the SYNAXYS App and are visible to everyone who can see the pull request. You can revoke the App’s access at any time in your GitHub settings; repositories are only connected after an administrator of the repository and of the workspace chooses to do so.

## 5. How AI code analysis works and what is sent to OpenAI

> **Relevant source code is transmitted to OpenAI for AI-powered analysis.**

For each review the service builds a request containing:

- the pull request title and the base and head branch names;
- the text of the changed files’ diffs (only files that qualify: binary, lock, generated, vendored and sensitive-named files such as .env or key files are skipped; very large diffs are truncated);
- any custom review rules defined in your workspace (name, severity, instruction);
- short code excerpts from other files in the same repository that were retrieved from the search index to give context (up to 4,000 characters each).

For indexing and search, code chunks (prefixed with their file path) and your search queries are sent to OpenAI to create embeddings. The models in use are set by the operator; at the time of writing the defaults are gpt-4o (reviews) and text-embedding-3-small (embeddings): requests go to OpenAI’s standard API endpoint, and this policy is updated if the models change.

Before sending, lines that match known secret patterns (for example access tokens and private keys) are redacted, and indexed chunks that contain such patterns are not indexed. This is best effort: it cannot recognise every secret or every kind of confidential information.

How OpenAI handles data it receives (retention, abuse monitoring, use for training) is governed by OpenAI’s API terms and data-use policies as they apply to the operator’s OpenAI API account, which OpenAI can change. We do not state any guarantee about this beyond those terms. The SYNAXYS software itself does not train or fine-tune models on your data.

Output of the AI (findings and suggested comments) is stored in our database and, when you publish it, posted to GitHub.

## 6. Code search and indexing: what is stored at Pinecone

When you index a repository (or a branch), the service reads eligible files from GitHub (within size and file-count limits that the operator configures; .gitignore’d, generated, vendored, binary and sensitive files are skipped), cuts them into chunks and stores them at Pinecone, in one namespace per repository.

- Stored per chunk: the embedding vector and metadata: repository id and full name, branch, commit, file path, language, start and end line, and up to 1,500 characters of the chunk’s text.
- Hosting region and plan: us-east-1.
- Removal: vectors of a file are removed when the file is deleted or re-indexed; a branch’s vectors when its index is removed or GitHub reports the branch deleted; all vectors of a repository when it is disconnected, when its workspace is deleted, or when the account of a workspace’s only member is deleted.

## 11. Deleting and exporting your data

- Export: Settings → Account → “Export your data” produces a ZIP of your account data (profile, memberships, review rules, activity, notifications, and the reviews, findings and comments of repositories you can access). It never contains credentials. It can be downloaded only by you and expires after 24 hours.
- Delete your account: Settings → Account. You must type your GitHub username and have signed in within the last 15 minutes. Your profile, sessions, stored GitHub token, notifications and exports are deleted and we ask GitHub to revoke the token (best effort: deletion does not depend on GitHub’s answer). Workspaces you share with others continue (ownership passes to another member). A workspace in which you are the only member is deleted with all review data and search index of its repositories.
- Delete a workspace (owner): removes the workspace and all review data and search index of its repositories.
- Remove comments on GitHub: administrators can delete comments published by SYNAXYS from the review page.
- To exercise other rights or if something cannot be done in the product, contact vaibhavverma0307@gmail.com.

## 12. Security measures

- Transport encryption between your browser, our servers and the providers (HTTPS).
- GitHub user tokens are encrypted at rest; sessions store only a hash of the cookie; webhook calls from GitHub are verified with a signature before processing.
- Access is checked on the server for every request, by workspace membership and role; data of one workspace is not reachable by members of another.
- Protections against cross-site request forgery, rate limiting, security headers, secret redaction in logs, and monitoring of failed jobs.
- No system is perfectly secure; see our vulnerability reporting policy (the Security page of this service).
